## 三、WorkBuddy 状态数据源（已实测定位）

### 3.1 数据在哪里

```
C:\Users\28679\.workbuddy\tasks\<会话ID>\<任务ID>.json
```

单条结构：

```json
{
  "subject": "制作交互原型 Demo",
  "description": "制作 3 个可点击核心流程的 HTML 原型……",
  "activeForm": "制作交互原型 Demo",
  "status": "in_progress",
  "id": "10",
  "createdAt": 1789396331410,
  "updatedAt": 1789396776373
}
```

实测统计（当前共 148 条）：`completed` 126 · `pending` 16 · `in_progress` 6

### 3.2 字段映射

| 桌宠提示 | 数据来源 | 判定规则 |
|---|---|---|
| **正在处理 x 个任务中** | 当前会话下的 `tasks/*.json` | `status === "in_progress"` 计数 |
| **有 x 个任务需要确认** | 同上 | `status === "pending"` 计数 |

### 3.3 其它候选通道（已实测排除）

| 通道 | 实测结果 | 结论 |
|---|---|---|
| `~/.workbuddy/sessions/*.json` 中的 `endpoint`（如 `http://127.0.0.1:53349`） | 根路径 200，`/status`、`/health`、`/api/status` 等一律 **401** | 需鉴权，不采用 |
| `artifact-index/`、`changes-index/` | 是产物与变更索引 | 与任务状态无关 |
| `logs/`、`audit-log/` | 有记录但需解析日志 | 成本高，不作主通道 |

**结论：直接读 `tasks/` 目录的 JSON 文件最可靠** —— 无需鉴权、结构稳定、写盘即更新。

### 3.4 桥接方案（P1 实施）

在 Electron 主进程内做（不必另起独立服务）：

1. 定时扫描 `~/.workbuddy/tasks/`，以 `sessions/` 中 `lastHeartbeat` 最新的 `interactive` 会话为准，确定「当前会话」
2. 统计该会话下 `in_progress` / `pending` 数量
3. 通过 IPC 直接推给渲染进程的 `MiyoPet.setState({processing, pending})`
4. 桌宠端已预留该接口，**接入时无需改动原型逻辑**

### 3.5 一个语义问题（需老师确认）

「**需要确认**」目前我按 `pending` 任务数实现。但存在另一种可能：

- **方案 A（现实现）**：`pending` = 待办未开始的任务
- **方案 B**：指 WorkBuddy 的**权限确认请求**（工具调用待批准）

在 `tasks/` 里只观测到 `pending / in_progress / completed` 三态，**没有看到独立的「待确认」队列**。
如果老师指的是权限确认，需要另找信号源（可能在会话运行时内存里，未落盘）。请老师确认口径。
