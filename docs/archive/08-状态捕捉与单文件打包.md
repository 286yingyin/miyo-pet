## 一、状态获取机制

### 1.1 数据源（三级，按可靠性排序）

| 级别 | 位置 | 用途 | 可靠性 |
|---|---|---|---|
| 主 | `%CODEBUDDY_CONFIG_DIR%\tasks\<sessionId>\<n>.json` | 任务清单与状态 | 高：原地改写、mtime 与内部 `updatedAt` 差 < 2s |
| 主 | `%CODEBUDDY_CONFIG_DIR%\sessions\<pid>.json` | 判定「当前活跃会话」 | 高：心跳秒级刷新 |
| 主 | `%CODEBUDDY_CONFIG_DIR%\audit-log\{spool\*.jsonl, YYYY-MM-DD.jsonl}` | **权限待批准**信号 | 高：成对事件可配对 |
| 兼容 | 会话暴露的本地端口 `http://127.0.0.1:<port>/status` | — | **不可用：一律 401** |

`%CODEBUDDY_CONFIG_DIR%` 默认 `C:\Users\<用户>\.workbuddy`，可用环境变量覆盖
（也支持 `WORKBUDDY_TASKS_DIR` 单独指定任务目录）。

任务 JSON 的字段固定为：
```json
{ "subject","description","activeForm","status","id","createdAt","updatedAt"[, "metadata"] }
```
- `status` ∈ `in_progress | pending | completed`
- ⚠️ 任务被**取消**时 `status` 仍可能是 `in_progress`，取消标记在 `metadata.cancelled`

### 1.2 当前会话判定（有陷阱，必须走兜底链）

`tasks\<sessionId>\` 的目录名就是 sessionId，而 `sessions\<pid>.json` 里的 `sessionId` 与之同名
—— 所以可以用心跳文件反查「老师现在在用哪个会话」。

**陷阱**：本机实测存在 `sessions\15328.json`，心跳最新，但它的
`sessionId = "interactive-15328"`、`cwd` 指向临时目录，**没有对应的 tasks 目录**。
只按「心跳最新」会锁到一个空会话，数字全变 0。

判定算法（`scripts/state-core.js`）：

1. 读全部 `sessions\*.json`，过滤掉**没有对应 tasks 目录**的；
2. 优先取 `cwd` 命中当前工作目录的会话；
3. 否则取「有未完成任务 且 心跳最新」的；
4. 再否则退化为「tasks 目录下 mtime 最新的会话」；
5. 全都失败 → `session=null`，并置 `degraded=true`（**降级不是归零**）。

判定结果会连**理由**一起输出，便于排查：
```
[state-core] 会话 {"session":"60d8f0c0-…","reason":"cwd 命中当前项目","file":"…\\sessions\\21388.json"}
```

### 1.3 权限待批准信号（与「待办」严格区分）

`audit-log` 里是**成对事件**：

| 事件 | 含义 |
|---|---|
| `*.needs-approval` / `*.detected` 且 `decision==="info"` | 出现待批准请求 |
| `…approved` / `…approval-resolved` / `…approval-timeout` / `…original-reuse` | 该请求已收尾 |

配对键：**`toolCallId` + `requestId`**（实测事件里**没有 `sequence` 字段**）。
⚠️ 同一个 `requestId` 下可能对应**多个 `toolCallId`**，必须逐个配对，不能只看 requestId。
未配对的 `needs-approval` 即为「待批准」，超过 TTL（默认 30 分钟）自动失效。

于是桌宠同时区分三个数：
- `processing` = `in_progress` 任务数 → 「正在处理 x 个任务中」
- `pending` = `pending` 任务数 → 「有 x 个任务待办」
- `approval` = 未收尾的待批准请求 → **独立的「待批准」表情与提示**

### 1.4 聚合范围

| 范围 | 规则 |
|---|---|
| `current`（默认） | 只统计当前会话 |
| `all` | 统计全部会话；**超过 7 天未动的未完任务计入 `stale`，不进数字**（另有角标提示） |

实测效果：旧实现报「待确认 20」（含 9 月的历史残留），切到 `current` 后只报**真实在办的 5 条**。

## 二、触发时机

`electron/main.js` 采用「**事件驱动 + 兜底轮询**」，两者互补：

### 2.1 fs.watch 监听的路径

| 监听对象 | 目的 |
|---|---|
| `tasks\` 根目录 | 新会话出现 |
| `tasks\<当前会话>\` | 任务增删改 |
| `sessions\` | 活跃会话切换 |
| `audit-log\spool\` | 权限事件实时流（`audit-spool-<pid>-<日期>.jsonl` 正在被写） |
| `audit-log\` | 每日归档文件轮转 |

### 2.2 去抖参数（实测调出来的）

| 参数 | 值 | 原因 |
|---|---|---|
| 事件去抖 | 350 ms | 任务创建时会**批量落盘**（同会话多个文件 mtime 完全相同），必须合并 |
| 收敛等待 | 300 ms | 文件可能正被写入，等一拍再读更稳 |
| 兜底轮询 | **2000 ms，永不取消** | fs.watch 在 Windows 上会漏事件；且网络盘/清理工具会导致 watcher 失效 |
| `rev` 单调递增 | 每次快照 +1 | 渲染层据此**拒绝过期数据**（见 §3.2） |

### 2.3 「写入中」的处理

读取失败**绝不视为「任务消失」**：`state-core` 维护 `lastGood` 快照，
任何一次读失败都沿用上次已知值，并把 `ok=false / degraded=true` 一起上报。
`justDone`（全部完成）**只在 `ok===true` 的快照上才允许产生** —— 这是防止
「文件被占用 → 读成 0 条 → 误报『全部完成』」的关键护栏。

## 三、异常处理

逐条列明「处理动作 → 对外表现」。原则：**宁可降级显示旧值，也不给出错误的新值。**

| 异常 | 处理动作 | 对外表现 |
|---|---|---|
| 配置目录不存在 / 环境变量缺失 | 逐级回退默认路径；全部失败则 `ok=false` | 桌宠停在上一状态，气泡提示暂时读不到状态 |
| 单个 JSON 解析失败 | 跳过该文件并计入 `errors[]`；**不参与任何计数** | 数字不变；设置页「最近变化」里能看到降级记录 |
| 0 字节 / 全 `\0` 文件（**实测确有**：`sessions\20920.json`、`21656.json`） | 判定为损坏，同上跳过；读取带重试 | 同上 |
| 文件被占用 / 临时读失败 | 沿用 `lastGood`，`degraded=true` | 数字冻结（不会归零） |
| 编码异常 | 以字节读入、按 UTF-8 容错解码，失败则跳过该文件 | 同上 |
| 会话无法判定 | `session=null` + `degraded=true`，退回「统计全部」 | 气泡提示「没能确定当前会话」 |
| `audit-log` 被轮转 / spool 换 pid | 重新解析目录，取当前 spool 名（含 pid 与日期） | 权限数短暂为 0，下一拍恢复 |
| 无权限读取 | 记入 `errors[]`，不中断其他数据源 | 部分数字缺失，其余照常 |
| `history` 目录不可写 | **降级到内存环形缓冲**（只留最近若干条） | 设置页仍能看到最近变化，只是重启后不留存 |
| 快照内容无变化 | 不写日志、不推 IPC（按 `rev` 比对） | 无多余抖动 |

## 四、状态变化的记录

### 4.1 落盘

- 位置：`%APPDATA%\miyo-pet\history\changes-YYYY-MM-DD.jsonl`（**按天分文件**）
- 追加式写入，单条一行 JSON：

```json
{"ts":1791803732428,"iso":"2026-10-12T19:15:32+08:00","seq":6,
 "kind":"state","source":"boot","scope":"current",
 "session":"60d8f0c0-8ab4-4644-8719-fe0a8f902b7d",
 "prev":{"processing":1,"pending":1,"approval":0,"completed":8,"rev":1},
 "next":{"processing":1,"pending":1,"approval":0,"completed":8,"rev":1},
 "reason":"窗口就绪","degraded":false,"errors":[]}
```

字段设计要点：`kind`（`boot`/`state`/`health`）、`source`（`watch`/`poll`/`boot`/`settings`）、
`prev`/`next` 前后值、`reason` 人类可读原因、`degraded` 与 `errors` 供排查。

- 轮转：单文件 > 2 MB 换新文件；只保留最近 **14 天 / 30 个文件**
- 原子性：单行一次 `appendFileSync`（追加写不破坏已有内容）
- **无变化不写**（`diffEntry` 返回 `null`）

### 4.2 查看

设置窗口（右键桌宠 → 设置…）里有「**最近变化**」表，显示时间 / 类型 / 前后值 / 原因，
另有「打开历史文件夹」按钮。取数走 IPC：`getHistory(n)` / `historyStats()` / `openHistory()`。

## 五、在程序中的体现

### 5.1 状态机（v2 共 9 态，v1 亦已补齐）

优先级：`error > approval > pending > processing > done > 空闲档位`

| 状态 | 触发 | 体现 |
|---|---|---|
| `processing` | 有 `in_progress` | 差分图 + 工作动画 + 胶囊「正在处理 x 个任务中」 |
| `pending` | 有 `pending` 任务 | 待办表情 + 胶囊「有 x 个任务待办」 |
| **`approval`** | 有未收尾待批准请求 | **独立表情** + 暖色呼吸胶囊「有 x 项待批准」 |
| `done` | `justDone`（计数由 >0 变 0，8 秒时效） | 喜悦表情 |
| `error` | 快照 `ok=false` 持续 | 出错表情 |
| `idle_5/15/30` | 空闲 5/15/30 分钟 | 困惑 → 生气 → 冒烟 |

### 5.2 渲染层的三条通道仲裁（本次修掉的核心缺陷）

原先 `status.json` 轮询 / `postMessage` / 宿主 IPC 三条通道各自为政，**陈旧的 `status.json`
可能覆盖 IPC 推来的实时值**。现在：

- 页面检测到 `window.petHost` → `HOSTED=true`，**彻底关闭 `status.json` 轮询与 postMessage**
  （这两条只服务于「用浏览器直接打开原型」的开发场景）；
- 所有入参统一过 **`rev` 单调闸**：`patch.rev < lastRev` 直接丢弃。

### 5.3 `setState` 接口扩展（向后兼容）

新增字段：`rev / approval / justDone / ok / degraded / error / stale`。
旧调用 `MiyoPet.setState({processing, pending})` 行为不变。
对外接口两版保持一致：
`setState / getState / getMode / getSpr / getMapping / setMapping / react / liveLine / reaction / isHosted / setApprovalVisible`。

## 六、单文件便携 exe

### 6.1 最终方案

```bash
node scripts/build-portable.js            # 内部驱动 electron-builder
```

产物：**`dist-single/miyo-pet-portable.exe`（141.3 MB）** —— 一个文件，双击即出桌宠。
做法：electron-builder 的 `portable` 目标（NSIS + LZMA），运行时解压到 `%TEMP%` 后启动。

| 产物 | 路径 | 说明 |
|---|---|---|
| **单文件便携** | `dist-single\miyo-pet-portable.exe` | 141 MB，一个文件即可分发 |
| 绿色目录版 | `dist\miyo-pet-win32-x64\miyo-pet.exe` | 335 MB，**启动最快**（无需解压） |
| zip 便携包 | `dist-single\miyo-pet-portable.zip` | 204 MB，解压即用 |

### 6.2 真机冒烟（实测输出）

```
进程：miyo-pet-0.1.0-portable.e（启动器）+ 4 × miyo-pet.exe
history：11 行 → 17 行
最新记录：{"iso":"2026-10-12T19:15:32+08:00","kind":"state","source":"boot",
          "scope":"current","session":"60d8f0c0-…",
          "next":{"processing":1,"pending":1,"completed":8}}
```

⇒ 单文件包不只是「能解压」，而是**状态链路在打包版里跑通了**。

### 6.3 走过的弯路（留作记录，别再重跑）

**(a) IExpress 自解压（Windows 自带，零下载）**
- 从 Git Bash 直接调用**永远不会成功**：MSYS 会把 `/N` `/Q` 这类开关当路径做转换，
  IExpress 收到垃圾参数后**静默退回 GUI 向导**（现象：卡住，或返回 0 但不产出文件）。
  必须 `MSYS_NO_PATHCONV=1`，或改由 Node `spawnSync` 调用。
  加上之后小包（3 个文件）确实能成。
- **但它在包变大时会静默失败**（`exit=1`、无输出、无日志、无中间 cab）。
  实测边界会随 payload 构成漂移：同一「条目数」、不同文件集，结果不同；
  把文件全换成 200 字节占位符仍复现 → **与体积无关**；
  往 SED 灌 42 KB 填充仍成功 → **与 SED 文本体积无关**；
  单独把 `index.html` 放进 3 文件小包又能成功 → **也不是文件名毒性**。
  找不到可靠规避规则 ⇒ 判定 IExpress 不适合本项目。

**(b) Info-ZIP `unzipsfx` 拼接（`cat unzipsfx.exe payload.zip > sfx.exe`）**
- 拼接与解压**完全可用**（EOCD 可识别、目录结构保留），且无体积上限。
- 但它**不能自动运行**：文档里「解压后运行命令」是编译期选项，
  PortableGit 的这份构建没有开；`$AUTORUN$` 注释虽被识别，执行前需要按键确认。
  ⇒ 只能解压、不能「双击即用」，故弃用。

**(c) 用 `unzipsfx` 之外的自解压壳**：本机没有 7-Zip / WinRAR / NSIS；
`csc.exe`（.NET 编译器）被安全策略拦截，无法自己编一个小启动器。

### 6.4 electron-builder 路线上的三个坑（脚本已自动绕开）

| 坑 | 现象 | 处理 |
|---|---|---|
| 子进程找不到 PowerShell/cmd | `Node module collector spawn (npm.CMD …) failed: spawn powershell.exe ENOENT` | 把 `System32` 与 `System32\WindowsPowerShell\v1.0` 加进子进程 PATH |
| safe-delete 护栏 | `SAFE_DELETE_BULK_CONFIRM_REQUIRED {count:115, threshold:50}` —— 构建开头要清空输出目录，而护栏拦住「单目录 >50 条目」的删除 | **每次换一个全新的输出目录**（脚本用 `%TEMP%\miyo-build-<时间戳>`），不与护栏较劲 |
| NSIS 资源下载超时 | `connect ETIMEDOUT …:443` | 可设 `MIYO_BUILDER_MIRROR` 走镜像；资源进缓存后不再下载 |

> 附带修正一条**此前的错误结论**：曾判定「本沙箱 Node 无法 spawn 子进程（EBUSY）」，
> 这是误判 —— Node 能正常 spawn（`spawnSync(process.execPath,['-v'])` → status 0，
> `tar.exe --version` → status 0）。当时的失败其实是 **PATH 里没有 powershell.exe**。
